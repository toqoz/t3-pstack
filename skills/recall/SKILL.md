# Recall

**Before you start or resume work, you rebuild the user's recent working context and hand back a tight capsule of where things stand now and what to do next.**

Keep it tight and on-topic. Read only what the in-scope threads need, then stop.

Your context lives in two records. Your own chat history holds what you did and decided. The shared record holds everything that happened around the same code under other names: the symptoms users keep reporting, the fixes that shipped and got reverted, the errors still firing in prod. That second record is what the **why** skill searches, across source control, the issue tracker, chat and issue channels, long-form docs, and error tracking. A feature with a long bug tail keeps most of its story there, so don't reconstruct it from your transcripts alone.

Use the current T3 project's thread API, not guessed transcript files. Discover the tool schemas. List with `t3_thread_list` scoped to the current project, excluding subagents, and page through `nextCursor` until the requested window is covered. The list is newest first; use returned timestamps, never UUID ordering. `t3_thread_search` can narrow candidates but is explicitly non-exhaustive and cannot prove that no matching history exists. Read a thread with `t3_thread_read` before making claims about it. Page `afterPosition` with `nextPosition`, and use `itemId`/`textOffset` with `nextTextOffset` for truncated text. Use `view: "activity"` when tool actions matter; message view alone does not establish execution. Preserve returned thread links verbatim. If history, required pages, or activity is unavailable, state the coverage gap instead of claiming complete recall. Do not widen to all projects or another machine unless asked. Determine list filter defaults from the current host documentation or observed response; do not assume unset settled/snoozed/status filters cover every thread. Use explicit filters or separate passes when supported, deduplicate IDs, and report uncertain coverage if defaults cannot be established. Judge the time window by returned last-activity timestamps. Do not assume list ordering is sufficient to stop early; finish enumeration when ordering semantics are unknown. Request adequate run metadata with `runLimit`; reaching an unpageable run limit is a gap for run-level claims, not proof of complete history. Never read an active delegated child thread as a polling substitute, including when named explicitly. Completed child result reads mark delivery; respect the host's ownership rules and disclose that effect when relevant.

1. Classify, then route. One specific prior chat to resume belongs to the session-pickup playbook, which is not yet available in this distribution; report the missing workflow rather than running a replacement procedure under recall. Turning habits into a durable skill is automate-me, also currently unavailable. A human-readable summary alone is a different task. Recall loads working context across recent chats before you act. If the user already gave you a full state capsule (paths, branch, the change), use it and skip the mining.
2. Lock the scope before searching. Pin the window ("recent" is a real range, default the last 7 days), the topic if named, and the workspace (default the active one. Never read another project's transcripts without being asked). State the scope back. Never quietly turn "all" into "recent N".
3. Fan out across your chat history. Spawn parallel subagents on a fast, cheap model, each taking a slice of the scoped thread corpus. Preserve this selection criterion: choose an available model/settings combination for low-cost, responsive history extraction, respecting an explicit model request for this task. Resolve availability/options through the live T3 catalog. Select a suitable efficient/small available model or routine-work effort autonomously and state the choice as a heuristic, not measured speed/cost evidence. Missing pricing/latency metadata alone does not require a question. An explicitly requested unavailable model or fixed option requires a user choice. Do not inherit another workflow's role defaults or the parent model merely for dispatch convenience. Read `references/models.md` for the job-based effort/speed rules and budget location, not another workflow's model choice; apply routine-work effort to the independently selected mining model.

The parent dispatches these mining roles directly under the host's T3 rules. Use native subagents only for a supported model on the current provider with no settings beyond the parent. Use delegate_task for another provider, explicit settings, isolation, or background work. Before the first delegation, inspect orchestrator_capabilities once and put settings in target.options. Follow the returned next; never poll delegates, and cancel any abandoned delegate with task_cancel. Children mine their assigned slice themselves and do not dispatch more agents.

Give each worker its selected model/settings, exact thread IDs, project/window/topic boundaries, and the thread-read instructions above. Order candidates by returned last-activity timestamps, never UUID names; inspect metadata and topic-relevant messages before larger regions. Skip the current chat, subagents, evals, and test noise. Each returns one block per relevant chat: topic, the user's goal, decisions, open threads, struggles and corrections, and artifacts (PRs, tickets, branches), citing the returned thread link. For one or two chats, skip the fan-out and read directly. Raw activity stays in workers; the parent receives findings and coverage gaps. Pass source/template/companion pointers as absolute paths from this distribution; do not substitute installed namesakes. Reading a coordinator skill is context, not permission for a child to execute it.
4. Sweep the shared record whenever the topic names a feature, file, subsystem, area, or bug. This is the default, not a judgment call, and "my work on X" does not exempt it. Hand it to the **why** skill's source investigators, but steer their question from "why was this built this way" to "what's the current state, what's been tried and didn't hold, and what are users still reporting". Reuse its per-source playbooks, run the investigators in parallel with the chat-history mining, and inherit its posture: one investigator per source, null results are findings, skip an unavailable MCP and say so. Fold what comes back into the brief. Skip this step only for pure activity recall with no named target ("what did I do this week"), where your own history and live state are the entire answer.
5. Verify against live state. Take the PRs, branches, and tickets that the mining and the sweep surfaced and check them with `git` and `gh`. When the answer hinges on what an agent actually did (the tools it ran, files it read, errors it hit), read the relevant thread activity, following pagination and truncation offsets. If the available record cannot establish the action, report the evidence gap rather than inferring an action or status from a summary. Do not invent an output status or claim required live verification completed.
6. Write the brief to the contract below. Group by thread. Stay on the named topic.

## Output contract

Lead with the capsule, then the thread status, then the problems, then the next move. Deeper detail goes below or gets cut.

- **Capsule.** At most 5 bullets. What this work is and where it stands overall.
- **Threads.** One line each, prefixed with exactly one status tag: `[merged #N]`, `[open PR #N]`, `[in flight <branch>]`, `[verified, uncommitted]`, `[reverted #N]`, or `[planned, not started]`. A thread with no tag is not done yet, so tag it.
- **Problems.** At most 5, the recurring ones. Include the symptoms users keep reporting and any fix that shipped and was reverted, so the next attempt starts where the last one failed.
- **Next move.** The single most useful next action, concrete.

An adjacent feature or ticket stays out unless it blocks this one. When the capsule and thread lines outgrow a screen, cut detail before you cut threads. Write the brief through the **unslop** skill, cite chat findings with the returned T3 thread link verbatim and shared-record findings by their source (PR #, ticket ID, chat permalink, error-tracker issue), and sanitize private context before any public output.

**Reply:** the brief, to the contract above.
